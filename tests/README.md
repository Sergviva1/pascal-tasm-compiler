# Тестовые данные

Файлы соответствуют сквозному примеру из §4 [ТЗ](../docs/SPEC%20%D0%A1%2B%2B.md): процедура `Compare` сравнивает число с `Limit` и меняет boolean-переменную через `var`-параметр.

| Файл | Назначение |
|---|---|
| `example.pas` | Исходная программа Pascal |
| `tokens.lst` | Эталонный JSON-массив токенов, вход парсера |
| `tree.json` | Эталонное AST, вход кодогенератора |
| `symbols.tab` | Эталонная JSON-таблица символов, вход кодогенератора |
| `fixture_tests.cpp` | Проверка формата и ключевых свойств эталонного примера |
| `codegen_regression_tests.cpp` | Регрессии кодогенератора: сегменты, внутренние ASM-имена, процедура `global` |

Эти данные не зависят от языка реализации компилятора. Переписывать их при переходе на C++ не нужно. `.lst` и `.tab` — JSON, не произвольный текст.

## Автоматическая проверка фикстур

Из корня репозитория:

```bash
mkdir -p build
g++ -std=c++17 -O2 -Wall -Wextra -Wpedantic -I. -o build/fixture_tests.exe tests/fixture_tests.cpp
./build/fixture_tests.exe tests
```

Или через CMake/CTest — команды в корневом README. Помимо проверки фикстур, CTest запускает тесты объявлений и семантики парсера, а также интеграционную цепочку `tokens.lst → parser → codegen → program.asm`.

Проверяются читаемость JSON, строковые значения токенов, типы и монотонность номеров строк, единственный конечный `EOF`, ключевые узлы AST, числовые/boolean-значения и сигнатура процедуры с `var`-параметром. Порядок записей таблицы символов несущественен.

Сам `fixture_tests` остаётся ограниченной проверкой **эталонного примера**, а не полной валидацией схемы и не повторной лексической обработкой исходника. Он не запускает модули и не создаёт промежуточные файлы; отдельный CTest-тест `parser_codegen_integration` запускает парсер и кодогенератор в изолированном каталоге сборки.

CTest-тест `codegen_regressions` разбирает тестовые потоки токенов настоящим
парсером и передаёт AST/символы генератору. Проверяются настройка near-stack
(`SS = DS` с сохранением физического адреса стека), передача глобальной/локальной
переменной и обычного параметра как `var`, перенаправление `var`-параметра,
конфликты Pascal-имён с регистрами/метками ASM и затенение имён в процедуре
`global`. Перестановка записей таблицы символов не должна менять результат.
Это проверки текста ASM и арифметики адресов, а не исполнение машинного кода;
проверка сборки и запуска через TASM/TLINK остаётся отдельным этапом.

## Изолированная проверка после реализации модулей

Все команды выполняются **из корня**, чтобы результаты не затёрли эталоны:

```bash
# Лексер: результат tokens.lst сравнить с tests/tokens.lst.
./build/lexer.exe tests/example.pas

# Парсер: использовать готовый эталонный поток токенов.
# Результаты tree.json и symbols.tab сравнить с одноимёнными файлами tests/.
./build/parser.exe tests/tokens.lst

# Кодогенератор: использовать эталонные AST и таблицу символов.
./build/codegen.exe tests/tree.json tests/symbols.tab
```

Сравнивай JSON по структуре и значениям, не по отступам или порядку ключей объектов. Порядок токенов и операторов AST важен; порядок записей таблицы символов — нет. Проверяй также области видимости и `paramsSignature`, не только имена.

После реализации лексера прогони все три стадии последовательно, как показано в README. Ошибки, выражения, области видимости и `var`-параметры отдельно покрывает набор `parser/parser_tests.cpp`; интеграционный CTest пока использует один эталонный поток токенов. ASM нужно отдельно собрать через TASM/TLINK и проверить в DOS-окружении.
