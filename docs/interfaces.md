# Границы компонентов, ЛР № 1 (вариант № 10)

Основание: два отчёта в `check/`, `check/roma lexer/{Token.h,TokenStorage.h,Lexer.cpp}` и `check/egor codogen/generator.cpp`. Ниже различены фактическое поведение и предлагаемый способ соединения; письменное подтверждение напарников ещё нужно.

## Лексер → наш парсер

- В C++ уже есть `Token { TokenType type; std::string lexeme; int line; int column; }`. Позиции начинаются с 1. Идентификаторы сохраняют исходный регистр, ключевые слова распознаются без учёта регистра. Имена нормализуем у себя, а диагностику показываем по исходной лексеме. `DECIMAL_INTEGER` несёт строку цифр, не готовое значение `int`. Минус — отдельный `MINUS`.
- Для `begin`, `end` и конца ввода используем именно `TokenType::BEGIN_KW`, `END_KW`, `END_OF_FILE`; строки `BEGIN`, `END`, `EOF` — вывод для человека. У EOF лексема `"EOF"`. Не требуем от Ромы переименований.
- Предлагаемый вызов: проверить `lexer.analyze()`, только при `true` передать `lexer.getTokens()` в парсер по `const TokenStorage&`. Хранилище принадлежит лексеру, копирование запрещено; не сохранять ссылки после его уничтожения. При `false` поток может содержать и другие токены, и EOF — это **не** разрешение продолжать разбор. Автономные тесты могут использовать `TokenStorage::add` без лексера.
- `const`, `procedure`, `if`, `then`, `else` и сравнения уже распознаются. Наличие ключевого слова в enum не обязывает парсер поддерживать всю грамматику Pascal. Для ЛР № 2 нет реализации hex и строк (строковый тип токена объявлен); к ЛР № 4 нужны `@` и `^`.

## Наш парсер → генератор

- Текущий `Program` хранит два массива ёмкостью по 100: имена переменных и `Assignment {target, expression}`. Сохраняем порядок объявлений и операторов. У `Expression` для `NUMBER` значимо `number`, для `VARIABLE` — `name`. Имена приводим к нижнему регистру: у Егора поиск по точному совпадению. Позиции и таблица символов остаются у нас.
- `bool generate(const Program&, const char* path)` уже работает без файла обмена. Объект принадлежит вызывающему коду до возврата. Генератор проверяет размеры, дубли, имена получателя и источника, вид выражения и диапазон литерала −32768…32767; сообщает ошибки в stderr. Проверки генератора не заменяют нашу диагностику парсера и семантики.
- Для интеграции вынести **существующие**, а не параллельные определения в общий заголовок; отделить `main()` генератора от библиотечной функции. Путь к ASM передавать из драйвера: демонстрационный `TASM\\program.asm` рассчитан на Windows. Платформа результата — Intel 8086/DOS, TASM + TLINK; просмотр значений — Turbo Debugger в DOSBox по отчёту Егора.

## Что показала проверка

- Сборка обоих примеров из C++17-исходников прошла. На файлах Ромы T1–T4 коды возврата лексера — `0, 0, 2, 2`. Для T3 фактически `#` в `4:9`; для T4 — `@` в **`3:11`**, а не `3:8`, как в `tests/EXPECTED.md`. T2 фактически не содержит ни `var`, ни запятой вопреки описанию теста. Это корректный лексический вход, но не готовый пример обмена с генератором: для него нужны объявления.
- В отчёте Ромы раздел «Цель работы» описывает генератор Intel 8086; раздел «Формулировка задания» относится к лексеру. Не переносить чужую цель в наш отчёт.
- Запуск демонстрационного `main` Егора создаёт ASM для `x := 10`. В его отчёте есть второй положительный тест (`x := 7; y := x; x := 25`) и два отрицательных (пустое имя источника, `40000`); имеющийся `main` не является запускателем всех четырёх. Результаты исполнения в DOSBox берём из отчёта, а не выдаём за собственный прогон. Для сквозной проверки подаём свою программу с `var x, y: integer;`, для защиты готовим также собственные автономные тесты парсера.
